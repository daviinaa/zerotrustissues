Automated GAN fraud detection deployment

MSc Cyber Security dissertation · Python, FastAPI, Docker, GitHub Actions, Azure AKS, Prometheus, Grafana, Locust

A feasibility study: can a GAN-based credit card fraud model be deployed through an automated CI/CD pipeline to Kubernetes without losing accuracy, and what does that automation actually buy you? The contribution is the pipeline, not a new model.

The problem

Most fraud detection research stops at a notebook and a results table. Very little of it asks what happens when you put the model behind an automated deployment pipeline: does it behave the same once it is containerised and running on different hardware, how long does the pipeline take, and what does it cost in latency and resources? The MLOps literature also describes plenty of adoption barriers, so I wanted to see which ones I would actually hit.

I took a GA-GAN fraud model adapted from Ge et al. (2025), "Gated attention based generative adversarial networks for imbalanced credit card fraud detection", trained it on the public European credit card dataset (284,807 transactions, 492 of them fraud, 0.17%), and built the pipeline around it. The dataset is PCA-anonymised: 30 features (Time, V1 to V28, Amount) and no demographic fields.

Research questions

  1. Performance. Does an automated CI/CD pipeline preserve the model's fraud detection performance compared with a manually deployed baseline? Success: a difference below 0.01 in precision, recall, F1 and AUC.
  2. Efficiency. How much does automation reduce deployment time and operational complexity? I measured this as safety scope (which checks run) as well as time.
  3. Non-functional behaviour. What does the pipeline mean for inference latency and resource use under load? Success: p99 below 500 ms at 100 concurrent users with zero failures.
  4. Feasibility. How do the findings line up with the MLOps adoption barriers in the literature?

Architecture

Three layers. Training runs by hand on my machine. Serving is a FastAPI app in a Docker image with the model baked in. CI/CD runs in GitHub Actions and deploys to a single-node Azure Kubernetes Service cluster (Standard_D2als_v7: 2 vCPU, 4 GB, AMD64). Prometheus and Grafana handle monitoring.

The model

The GA-GAN's generator maps a 100-dimensional latent vector through layers of 128 and 128 units to 30 features. The discriminator uses two Conv1d layers, gated self-attention and fully connected layers. The GAN is trained on the training-set fraud rows only, then generates synthetic fraud until the classes are balanced. The model that actually gets served is the classifier trained on real plus synthetic data: a 4-layer MLP (30, 150, 50, 25, 1) with LeakyReLU and a sigmoid output, 13,501 parameters in total.

Hyperparameters follow the released code rather than the paper text: batch size 1000, 10 GAN epochs, 10 classifier epochs, learning rate 0.002. I found ten discrepancies between the paper and the code along the way.

The API

Three endpoints: /health, /predict (1 to 1000 transactions, each exactly 30 floats) and /metrics for Prometheus. Six custom metrics cover prediction latency, request latency, request count by status, fraud detected, model load time and transactions processed. Inputs are z-score scaled with the training-split mean and standard deviation stored in scaler.json.

The image is python:3.11-slim with CPU-only PyTorch (about 500 MB), runs as a non-root user, has a Docker HEALTHCHECK and one uvicorn worker. On Kubernetes it runs as 2 replicas with liveness and readiness probes on /health, CPU requests of 250m and limits of 500m, memory 256Mi and 512Mi, behind a LoadBalancer service.

CI/CD stages and the gate

CI runs on every push or pull request to main: Python 3.11, the inference dependencies, then the 18 unit tests with coverage. The full suite is 20 tests (18 unit, 2 integration) with 91% coverage of the inference module.

CD runs on push to main or manual dispatch, with a concurrency lock so two deployments never overlap:

  1. test: record the start time, run the tests, then run the model evaluation gate against the checkpoint that will be deployed.
  2. build-and-push: build the image on an AMD64 runner, tag it with the git SHA and latest, push it to the container registry.
  3. deploy: log in to Azure, fetch cluster credentials, patch the manifest with the new image, apply the app and monitoring manifests and wait on rollout status for up to 300 s. If the rollout fails, rollout undo runs and the job fails. Then an in-cluster curl to /health and the timing output.

The gate lives in scripts/evaluate_gate.py. If any metric falls below its threshold the script exits 1 and nothing is built or deployed. I set the thresholds conservatively below the 10-epoch baseline:

Results

Same predictions in three environments (RQ1)

I sent all 56,962 held-out test transactions (98 fraud) through the API in each environment, in batches of 500 at a threshold of 0.5.

Model metrics on the test set by environment
MetricLocal (ARM64 macOS)Minikube (AMD64)AKS (AMD64)Delta
Precision0.78890.78890.78890.0000
Recall0.72450.72450.72450.0000
F10.75530.75530.75530.0000
AUC0.94610.94750.9475+0.0014

The confusion matrix was identical everywhere: 56,845 true negatives, 19 false positives, 27 missed frauds and 71 caught. Every single classification decision matched. The small AUC shift comes from ARM64 versus AMD64 floating-point differences in the maths libraries, and no binary decision changed. Getting to zero difference meant fixing a scaler seed mismatch first (42 against 123), which I write about in Same model, three environments.

For context, the paper reports AUC 0.929, precision 0.903, recall 0.848 and F1 0.875. My AUC is higher but precision, recall and F1 are lower, which fits training for 10 epochs.

CD run times (RQ2)

Timing from the CD workflow, two consecutive runs
RunTest + buildDeployTotal
Cold2m 19s5m 38s7m 57s
Warm2m 05s1m 10s3m 15s

The warm run was 59% faster overall and the deploy stage 79% faster. The manual path takes about 2 minutes, so the pipeline is slower. What it adds is the tests, the gate, AMD64 builds, health checks, rollback and an audit trail of deployments. When manual cloud deployments went wrong during the project, each incident took 30 to 60 minutes to sort out. The finding is structural enforcement, not speed.

Errors along the way (RQ4)

I documented 13 errors across 7 phases and mapped them to MLOps adoption barriers. The automation itself caught 8 of them. One pattern stood out: a failed provisioning step silently dropped the role assignment that lets the cluster pull images from the registry, and the failure only showed up later as a deployment problem. Feasibility comes out positive but conditional on infrastructure expertise, artefact governance and accepting extra complexity.

Limitations

      
    
        
  • Only inference deployment is automated. Training, including the GAN, ran by hand. There is no automated data ingestion.
    • 
        
  • 10-epoch training, so precision and recall sit below the paper's figures.
    • 
        
  • One public dataset. It is PCA-anonymised with no demographic fields, so fairness across groups could not be measured at all.
    • 
        
  • A single-node AKS cluster with no autoscaling, and 30-second load tests run from my own machine, so latency includes the network.
    • 
        
  • The manual baseline is one run, by me.
    • 
        
  • Zero delta is helped by a deterministic MLP. A stochastic model might not reproduce exactly across environments.
    • 
        
  • No model registry. MLflow was deferred, so model versions rely on timestamped filenames. Images are tagged with the git SHA.
    • 
        
  • The deployed checkpoint, including the GAN generator weights, is in the public repo. The in-browser demo ships only the classifier.
    • 
      


      
Security gaps I identified but did not close

      
This is a research prototype in a production-like setting, not a production system. The dissertation lists what would have to change first:

      
    
        
  • The API loads the checkpoint with torch.load(weights_only=False), which allows arbitrary code execution from a malicious file.
    • 
        
  • Plain HTTP with no TLS, and no API authentication.
    • 
        
  • No request or audit logging, and no data-retention controls.
    • 
        
  • No Kubernetes NetworkPolicies.
    • 
        
  • No security or vulnerability scanning in CI/CD, no encryption at rest for model artefacts, and no drift detection.
    • 
      

      
What does exist: a non-root container user, a slim image, resource limits, health probes, SHA-tagged images and deployment logs in GitHub Actions.


      
What I would do next

      
    
        
  • Add a model registry (MLflow or DVC) so model artefacts are versioned and traceable, not just images.
    • 
        
  • Harden the service: TLS ingress, OAuth2 or mTLS, a safe model format (weights_only=True, ONNX or SafeTensors), NetworkPolicies and audit logging.
    • 
        
  • Run training as a Kubernetes batch job so it goes through the same gates.
    • 
        
  • Run 5 to 15 minute load tests from a load generator inside the same region.
    • 
        
  • Replace the sed manifest patching with Kustomize or Helm.
    • 
        
  • Plan costs, and compare against serverless options.
