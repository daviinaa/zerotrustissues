Same model, three environments: what a 0.0014 AUC gap means

6 min read

One of the questions my MSc dissertation had to answer sounds almost too simple: if you push a fraud detection model through an automated CI/CD pipeline and run it on Kubernetes, does it still make the same decisions it made on your laptop?

Everyone assumes yes. It's the same weights, the same code, the same inputs. But "everyone assumes" isn't evidence, and in fraud detection a silent change in behaviour is exactly the kind of thing that hurts real people. So I tested it properly.

The setup

The model is a GA-GAN adapted from Ge et al. (2025). The GAN generates synthetic fraud to balance the training data, and what actually gets served is a small classifier: a 4-layer MLP with 13,501 parameters. It sits behind a FastAPI service in a Docker image, and the pipeline deploys that image to Kubernetes. (The full architecture is on the project page.)

I ran the same model in three places:

  • Local: on my Mac, ARM64.
  • Minikube: a local Kubernetes cluster running the AMD64 Docker image.
  • AKS: Azure Kubernetes Service, AMD64, deployed by the CD pipeline.

Then I sent every one of the 56,962 held-out test transactions through the API in each environment, in batches of 500, with a decision threshold of 0.5. Not a sample. All of them, including all 98 frauds.

Before running anything I wrote down what success looked like: a difference of less than 0.01 in precision, recall, F1 and AUC between local and deployed. Setting the tolerance up front matters. If you decide what "close enough" means after you've seen the numbers, you'll always find a reason to call it close enough.

The results

Precision, recall and F1 didn't move at all. The confusion matrix was identical in all three environments: 56,845 true negatives, 19 false positives, 27 missed frauds and 71 caught. Every single classification decision matched.

But AUC did move. 0.9461 on my laptop, 0.9475 on both minikube and AKS. A difference of 0.0014.

So what is that 0.0014?

Notice the pattern: the two AMD64 environments agree with each other exactly. The odd one out is my ARM64 laptop. That points at the hardware, not the pipeline.

Neural network inference comes down to a lot of floating-point multiplication and addition, handled by low-level maths libraries (BLAS) that are optimised differently for each CPU architecture. Floating-point arithmetic isn't perfectly associative, so adding the same numbers in a different order can give a result that differs in the last few decimal places. ARM64 and AMD64 builds do the sums slightly differently, so the probabilities come out very slightly different.

Why does that move AUC but not F1? Because they measure different things.

Precision, recall and F1 only care about the final yes/no decision at the 0.5 threshold. A probability of 0.31 versus 0.3100001 is still "not fraud". Unless a score sits right on the threshold, tiny numerical differences can't change the decision. None did.

AUC is different. It measures how well the model ranks every transaction across every possible threshold. It's built from the raw probabilities, so it's sensitive to the order of scores, not just which side of 0.5 they land on. If some scores sit very close together, a tiny numerical shift can swap their order, and because AUC is built from that ordering, it moves too. That's my reading of the mechanism; the dissertation attributes the shift to the ARM64 versus AMD64 maths libraries.

So the 0.0014 is real, it's explained, and it's well inside the 0.01 tolerance I set. More importantly, it changed zero decisions. For a fraud system, decisions are what customers experience. Nobody gets their card blocked by an AUC.

The bug I had to fix to get there

Here's the part I didn't expect. Getting to that table took a fix first.

The model expects its inputs z-score scaled: subtract the training mean, divide by the training standard deviation, for each of the 30 features. The training script computed those values but never saved them. So the inference side had a separate script that rebuilt them from the same 80/20 split and wrote them to scaler.json.

Except the two scripts didn't agree on the random seed for the split: 42 in one place, 123 in the other. A different seed means a slightly different training set, which means slightly different means and standard deviations, which means every input to the model is scaled slightly wrong. Nothing crashes. No test fails. The API returns perfectly plausible probabilities. They're just not the probabilities the model was trained to produce.

Fixing it to 123 everywhere is what got me to zero delta. It was one of 13 errors I documented during the project, and honestly it's the one I think about most, because it's exactly the kind of bug that survives code review. The code was fine. The artefact was wrong.

The lesson I took from it: preprocessing is part of the model. If your scaler lives in a different file from your weights, with its own script and its own history, you have two artefacts that must stay in sync and nothing enforcing it. That's why the in-browser demo on the project page bakes the scaling into the exported model graph. The browser sends raw features and can't get the preprocessing wrong.

How the paper compares

For context, the original paper reports AUC 0.929, precision 0.903, recall 0.848 and F1 0.875. My AUC is higher, but precision, recall and F1 are lower. The main reason is training length. I followed the released code, which trains for 10 epochs, not the 500 the paper text describes. Along the way I found ten discrepancies between the paper and the code. My dissertation was about the deployment pipeline, not about beating the paper, so I kept to the released code's settings.

What I'd tell someone running the same test

Compare decisions, not just aggregates. Matching F1 tells you the counts match. Matching confusion matrices across the full test set tells you something stronger. If I'd only looked at AUC, I'd have seen a 0.0014 shift and had no idea whether it mattered.

Expect cross-architecture drift in probabilities. If you develop on ARM and deploy on AMD64 (which describes a lot of us with Apple Silicon laptops), your scores won't be bit-for-bit identical. Decide in advance how much difference you'll tolerate.

Keep your gate thresholds away from the edge. My pipeline's evaluation gate requires AUC of at least 0.90. The model sits at 0.946, so a 0.0014 shift is irrelevant. If I'd set the gate at 0.946, the same model could pass on one machine and fail on another.

Be honest about why it worked. Zero delta was helped a lot by the model being a deterministic MLP. Same inputs, same weights, same outputs (within floating-point noise). A model with randomness at inference time, or one that depends on GPU-specific kernels, might not reproduce this cleanly. My result says the pipeline didn't break this model. It doesn't promise the same for every model.

The pipeline passed the test it was built to pass: the same model, deployed three ways, made exactly the same calls on every transaction. Getting there taught me more about artefact governance than any reading did. I wrote about that side of it in what the project taught me about AI governance, and about how the deployed service held up under load in load testing a fraud model on AKS and minikube.
