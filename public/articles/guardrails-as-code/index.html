Guardrails as code: treating AI rules like IAM

4 min read

This is the idea I keep coming back to.

Every company already decides what each employee can reach. Your role gets you into some systems and keeps you out of others, and that is written down as IAM policy, not as a reminder in a handbook. AI tools have not caught up. An engineer, an analyst and a support agent often get the same assistant, connected to the same tools, with the same rules: whatever the person remembers from training.

My idea is simple: treat AI rules like IAM. Guardrails as code.

What it looks like

Each role gets a policy file. The file says which MCP servers that role can use, which tools inside them, and what the assistant must refuse to do for that role. The files live in Git, change through review, and get tested like any other config.

Where it is enforced

On the repository. Put the rules and the MCP configuration in the repository itself. Everyone who pulls or clones that repository has already cloned the rules with it, without having to think about it. The guardrails travel with the code.

On the laptop. Repository rules have a weakness: the person who cloned them can edit them. So the stronger layer is a central policy installed on the laptop, managed by the company and not changeable by the user. I think this is the layer to build first.

What I haven't solved yet

  • Roles change. Who updates the policy when someone moves teams?
  • Blocks that are too strict make people work around them with personal tools.
  • Rules about content (do not paste customer data) are harder to enforce than rules about access (cannot use this MCP server).

This follows on from The prompt book and the anti book, which is about writing good practice down. Guardrails as code is about enforcing it. For the same idea applied to models rather than the people using them, see AI guardrails from a DevOps engineer's perspective.
